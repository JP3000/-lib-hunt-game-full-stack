# 改造前后对比：纯前端 → 全栈

> 旧版线上体验（纯前端）：<https://libhuntgame.com.cn>

## 改造前：一个能玩的 H5 游戏

```
浏览器
  │
  ├── 关卡数据、正确答案、二维码答案   ← 全部打包在 JS 里
  ├── 进度、得分                       ← localStorage
  └── 通关成绩                         ← POST 到 /api/results，写 JSON 文件
```

功能是完整的：12 关、扫码、道具、多语言、排行榜都能跑。问题不在"能不能玩"，而在"数据可不可信"。

| 问题 | 具体表现 |
| --- | --- |
| **答案在前端** | 打开 DevTools 搜 `correctOption`，12 关答案一目了然 |
| **判题在前端** | 分数由浏览器算出来再上报，改一行 JS 就能满分 |
| **进度在 localStorage** | 换手机、清缓存进度全丢；同一账号在不同设备是两份进度 |
| **没有账号** | 排行榜按昵称，重名、冒名无法区分 |
| **成绩是一份 JSON 文件** | 并发写会互相覆盖，无法分页、统计、导出 |
| **没有服务端约束** | 可以跳关、重复交卷、一关反复加分 |

这不是"实现得不好"，是**架构决定了业务真相在客户端**。要做防作弊、多设备、统计，就必须把真相搬到服务端。

## 改造后：服务端持有真相

```
浏览器
  │  只请求同源 /api/*
  ▼
Next.js 16（:3000）          页面、多语言、扫码、摄像头
  │
  │  rewrite（本地）/ Nginx 反代（生产）
  ▼
Spring Boot 3（:8080）       JWT、判题、计分、结算、限流
  │            │
  ▼            ▼
MySQL 8.4   Redis 7
内容/对局/成绩   排行榜 / 限流
```

浏览器依然只和 Next.js 通信，跨域、鉴权头、错误格式都在一层里处理；后端可以从任何客户端调用，不依赖前端框架。

## 逐项对照

| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 题目与答案 | JS bundle | MySQL；对外 VO 不含 `correct_option_keys` / `qr_answer` |
| 判题 | 浏览器 | 服务端 `GameRunService`，前端只提交选了哪些 key |
| 计分 | 浏览器 | 服务端 `GameRules`：每关 20，多选少选得部分分、错选不得分 |
| 进度 | localStorage | `game_run.last_level_no`，`GET /api/runs/current` 恢复 |
| 身份 | 无 | JWT + BCrypt；管理员创建 / 禁用 / 重置密码 |
| 防跳关 | 无 | 提交非当前关卡直接拒绝 |
| 防重复结算 | 无 | `level_attempt.settled` + `UNIQUE(run_id, level_no)` |
| 二维码 | 明文常量，可复制 | HMAC 签名 + 过期时间，服务端签发 |
| 防连点 / 并发 | 无 | `SELECT ... FOR UPDATE` 行锁 + 唯一索引兜底 |
| 排行榜 | JSON 文件 | Redis ZSET 复合排序，MySQL 兜底与重建 |
| 统计 | 无 | 管理端：玩家数、通关数、平均分、平均耗时 |
| 答案泄露面 | 全量 | 数据库 + 服务端内存 |

## 迁移策略

改造没有重写 UI，按 5 条规矩推进：

1. **UI 不重写，只改数据源**——组件、样式、动效一行没动，替换的是 `useGameStore` 背后的读写
2. **服务端是唯一真相**——前端不再做任何"最终判断"
3. **按垂直切片开发**——一次只打通一条链路（登录 → 开局 → 判题 → 结算），每片都能演示
4. **每个阶段有可验收的产物**——每次提交都附带 curl 结果或测试用例，见 [PLAN.md](../PLAN.md)
5. **不做的技术，理由要能讲出来**——微服务、MQ、关卡 CMS 都明确不做

前端改动集中在数据层：`src/lib/api.ts`、`src/store/game-store.ts`、各页面的数据获取。旧版的关卡内容（`src/data/levels.ts`）被迁进数据库，源文件保留为生成 SQL 的输入（`scripts/export-levels.mjs`），前端的 `src/lib/levels.ts` 已删除。

## 代价与取舍

| 代价 | 处理方式 |
| --- | --- |
| 从"一个静态站"变成"两个进程 + 两个中间件" | `docker compose` 一条命令拉起 MySQL / Redis；本地开发一个脚本起后端 |
| 接口多了，前端要处理加载 / 错误 / 未登录 | 统一响应体 `{code,msg,data}` + `apiFetch` 封装 + `AuthGate` |
| 内容改动要跑迁移 | 保留 TS 源文件与导出脚本；刻意不做 CMS（见 PLAN「明确不做」） |
| 从"一个静态站"变成"两个进程 + 两个中间件" | 作品集项目不部署，本地 `docker compose` 一条命令拉起 MySQL / Redis，面试时直接演示 |

## 改造带来的数字

- 后端 54 个自动化用例（Testcontainers 起真实 MySQL + Redis），覆盖判题、幂等、并发、二维码签名、限流、RBAC
- 压测：关卡详情每次回源 MySQL 时 3,027 req/s、P95 43 ms，详见 [perf/RESULTS.md](../perf/RESULTS.md)
- 现场二维码用 HMAC 签名 + 过期时间，服务端签发，客户端拿不到密钥
- 接口一览、架构图、环境变量都在 [README.md](../README.md)

## 如果重来一次

- 先写 `Result` / 异常 / 鉴权三件套，再写业务——后面每个接口都少写一遍样板
- 测试用例和功能同步写。改造中途补测试时，很多并发问题已经写进代码，只能靠回读来确认
- 压测要在 JVM 预热后做。第一次测出 61 req/s 差点以为代码写坏了，其实是冷启动 + Redis 故障重试叠加
