# 面试速览：图书馆寻宝游戏全栈改造

> 用途：面试前 10 分钟过一遍，能在 30 秒内说清项目，在 5 分钟内接住追问。
> 详细讲稿见 [INTERVIEW.md](INTERVIEW.md)，完整教学见 [PROJECT-GUIDE.md](PROJECT-GUIDE.md)。

---

## 1. 三句话介绍

**30 秒版**

> 这是一个 12 关的图书馆寻宝 H5 游戏。我把它从纯前端改成了 Spring Boot + MySQL + Redis 的全栈系统：答案、判题、计分、进度、排行榜全部由服务端负责，前端只提交“我选了什么、我扫到了什么”。重点解决的是并发下的幂等和一致性，写了 54 个自动化测试（集成测试跑在真实的 MySQL/Redis 容器上），也做了 JMeter 压测。

**90 秒版**（面试官说“介绍一下你的项目”）

> 玩家在图书馆里按线索找二维码，扫码 + 答题过关，12 关满分 240，同分比用时。
>
> 旧版是纯前端的：答案打包在 JS 里，分数由浏览器算，进度存 localStorage。能玩，但数据不可信，改一行代码就能满分。我把它改成前后端分离：Next.js 做页面和摄像头扫码，Spring Boot 做鉴权、判题、计分、结算和进度，MySQL 存内容和成绩，Redis 做排行榜和登录限流。
>
> 核心难点是并发：同一关的答题和扫码顺序不限，网络重试还会重复提交。我用幂等键、唯一索引、行锁和结算标记，保证“只加一次分”。验证上，集成测试用 Testcontainers 起真实 MySQL/Redis，覆盖并发、二维码签名、限流和权限；压测时关卡详情接口单机 3,027 req/s、P95 43 ms。

**一句话版本**

> 把一个“能玩但不可信”的纯前端游戏，改造成“服务端持有真相”的全栈系统。

## 2. 项目是什么

- **业务**：线下图书馆寻宝。每关两道验证——
  1. **答题**：图书馆检索知识，每关 20 分
  2. **扫码**：到指定位置扫二维码，服务端验签
- **规则**：两道都通过才结算；多选少选得部分分，选到错误选项本题 0 分，不倒扣；分数一旦通过就锁定
- **规模**：12 关 × 3 种语言（繁中 / 简中 / 英文），满分 240
- **角色**：学生（学号直登，`2 字母 + 6 数字`）、管理员（内容与数据看板）

## 4. 五个重点（面试主线）

### ① 服务端权威：答案和判题不在前端

- 关卡接口返回的 VO 不含 `correct_option_keys`、`qr_answer`、`password_hash`
- 前端只提交选项 key，服务端 `GameRules` 算分并返回结果
- 答错不提示答案，只允许重试；安全测试会断言响应里没有答案字段

**为什么重要**：旧版最大的问题是“业务真相在客户端”，改 JS 就能作弊。

### ② 并发与幂等：只加一次分

三道保险：

1. **开局**：客户端带 `Idempotency-Key`，`game_run.idempotency_key` 唯一索引兜底；换玩家复用同一个 key 会被拒绝
2. **答题 / 扫码**：先看 `question_passed` / `qr_passed`，已通过直接返回原结果
3. **结算**：`level_attempt.settled` 标记，谁最后完成都只有第一次加分

同一局的请求用 `SELECT ... FOR UPDATE` 锁 `game_run` 行串行化；`UNIQUE(run_id, level_no)` 作为最后保险。测试里 10 个线程同时提交，只落一条 attempt，`attempts = 10`。

**为什么不用 `synchronized`**：JVM 锁只在单实例有效，粒度还是整个方法；数据库行锁粒度是“一局”，多实例也成立。

### ③ 二维码：HMAC 签名 + 过期时间

- token 格式：`v1.<关卡号>.<过期秒>.<HMAC-SHA256>`
- 密钥 = 服务端密钥 + 该关卡的 `qr_answer`，客户端拿不到
- 默认有效期 7 天，管理端接口签发，TTL 限制在 60 秒 ~ 30 天
- 校验用常量时间比较，容忍大小写和首尾空格

**诚实边界**：签名防伪造，但在有效期内仍可被转发；要彻底防转发需要绑定玩家/对局或一次性 nonce，这是已知限制。

### ④ 排行榜：Redis ZSET + MySQL 兜底

- score 编码两个维度：`totalScore * 100000 + (100000 - durationSeconds)`
- 一次 `ZREVRANGE` 同时按“分数高、用时短”排序；满分 240，乘 10 万仍在 double 精确整数范围内
- member 存 `runId`，保留每一局，读取时按玩家去重取最好一局
- 通关后在**事务提交后**写 Redis；写失败只记日志，不影响通关
- Redis 不可用时自动查 MySQL 窗口函数；支持一键全量重建

### ⑤ 质量保障：真实容器 + 压测

- **54 个自动化测试**，其中集成测试跑在 Testcontainers 起的真实 `mysql:8.4` / `redis:7` 上
- 覆盖：判题规则、幂等、10 线程并发、排行榜降级、二维码签名、登录限流、RBAC、答案不泄露
- **压测**：`GET /api/levels/1?locale=zh-Hant`，JVM 预热后 `ab -n 5000 -c 50`，3,027 req/s、P50 12 ms、P95 43 ms、P99 71 ms（当前代码每次回源 MySQL）

**为什么不用 H2**：判题依赖 `FOR UPDATE`、JSON 列、窗口函数，这些都是 MySQL 特有行为，H2 测不出真实问题。

## 5. 3–4 个月怎么讲

不要把它讲成“时间短所以做得少”，讲成**范围控制得好**：

> 这个项目功能不多，3–4 个月主要不是花在堆页面上，而是花在“让数据可信”这件事上。UI 基本沿用旧版，我按垂直切片推进：登录 → 开局 → 判题 → 结算，每打通一条链路就能演示。后半程主要补并发、测试、压测和文档。

可以这样分配叙述（按你的实际情况调整）：

| 阶段 | 做的事 |
| --- | --- |
| 前期 | 数据从 JS 迁到 MySQL、账号与 JWT、关卡接口 |
| 中期 | 判题计分、开局/答题/扫码闭环、并发与幂等 |
| 后期 | 排行榜、限流、二维码签名、管理员看板 |
| 收尾 | Testcontainers 测试、JMeter 压测、文档与取舍复盘 |

**加分说法**：“我刻意没有做微服务、MQ、CMS，也没有为了炫技保留缓存——这个规模用不上，能讲清为什么不做，比多做两个模块更加分。”

## 7. 高频追问速答

| 追问 | 一句话回答 |
| --- | --- |
| 为什么不用 Spring Security？ | 只有两种角色，JWT 拦截器 + 角色注解足够；只用它的 BCrypt，避免整套过滤器链的复杂度 |
| 为什么不用 Redis 分布式锁？ | 锁的粒度是“一局”，数据库行锁已经够用；Redis 锁多一次网络往返，还要处理超时、续期、误删 |
| 行锁会不会把连接池拖垮？ | 压测里 20 线程并发判题，P95 26 ms、0 错误，Hikari 上限 10 没被打满 |
| 前端拿不到答案，怎么知道对错？ | 服务端返回 `correct`、本题得分和下一步动作；答案永远不出现在响应里 |
| 多选部分分会不会被刷满分？ | 本题一旦通过分数就锁定，不能重试补分；答错不提示，只增加尝试次数 |
| 二维码能被拍照转发吗？ | 有效期内可以，这是已知限制；要彻底解决需要绑定玩家/对局或一次性 nonce |
| Redis 挂了会怎样？ | 排行榜回落 MySQL 查询，登录限流降级；接口仍返回 200，但涉及 Redis 的请求会等待连接失败 |
| 为什么把缓存删了？ | 数据只有 12 关 × 3 语言，读 MySQL 已经够快；缓存一致性不值得维护 |
| 为什么不用 MQ？ | 没有需要异步削峰或最终一致性的场景；通关是同步事务，写排行榜用 `afterCommit` 就够 |
| 为什么测试要 Docker？ | Testcontainers 起临时 MySQL/Redis，行为与线上一致；跑应用本身不需要 Docker |

## 8. 主动说出的取舍（体现判断力）

- **不做微服务**：单实例、模块边界清楚，拆开只增加运维和联调成本
- **不做关卡 CMS**：内容只有 12 关，Flyway + 导出脚本足够；做 CMS 是给不存在的运营团队写功能
- **移除关卡缓存**：数据量小，直查 MySQL 的 3,027 req/s 足够；换来更少的失效逻辑
- **没有熔断器**：Redis 故障目前是 fail-open + 每次重试，延迟会变差；生产上应加 Resilience4j 或本地短路，这是明确写进文档的已知短板
- **二维码不是一次性**：TTL 内可转发，需要更强保证时再加 nonce / 绑定对局

## 9. 不要踩的说法

1. **不说线上 QPS**。项目是本地可运行的完整系统，数字都来自压测，不要说成“线上”。
2. **不说“分布式事务”或“强一致”**。只保证单库事务内的幂等和结算一次。
3. **不把历史压测数字说成当前**。混合场景 8,712 req/s 是当时带缓存的结果；当前关卡详情是 3,027 req/s。
4. **不说“二维码不可复制”**。准确说法是“防伪造、带有效期”。
5. **不说“用了 Spring Security”**。准确说法是“用了 BCrypt + 自写 JWT 拦截器”。
6. **不说“所有人都能满分”或“题目很难”**。计分规则是少选得部分分、错选 0 分、通过即锁定。
